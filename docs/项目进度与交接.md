## 4. 字数检测机制（2026-09-03 新增，本轮交付）

### 4.1 需求与设计

目标：篇幅尽量控制在 **2000–4000 字**（对应用户单章规范）。两种输入都覆盖：

- **单章文本** → 整段文本按 2000–4000 判定（unit=「全文」）
- **多章文本** → **逐章判定** + **平均单章字数**汇总（unit=「平均单章」）

### 4.2 档位表（src/lengthGuard.js，纯函数）

| status | 区间（字） | level | 说明 |
|--------|-----------|-------|------|
| empty | 0 | — | 未输入 |
| far-short | < 1000 | medium | 严重偏短 |
| short | 1000–1999 | low | 偏短 |
| ok | **2000–4000（含端点）** | — | 达标，不产生问题 |
| long | 4001–6000（含 6000） | low | 偏长 |
| far-long | > 6000 | medium | 严重偏长 |

核心导出：`LENGTH_TARGET`、`classifyLength(chars)`（含 deviation/suggestion 具体建议文案）、`summarizeLength(charsList)`。只依赖 `./util`（叶子安全）。

### 4.3 集成点

1. **src/commercialQuality.js**：QUALITY_CHECKS 新增 `chapter-length-out-of-range`。判定单元：逐章→ctx.chars；≥2 章→ctx.averageChapterChars；否则→ctx.chars。**触发下限 900 字**——既有的 `chapter-underdeveloped`（<900 字）已罚过短，此下限避免同一处重复扣分。points：far 档 8 分、近档 5 分。
2. **src/chapterAnalyzer.js**：每章挂 `lengthCheck`；summary 增加 `chaptersInRange` / `chaptersOutOfRange`。
3. **src/analyzer.js**：`analyzeNovel` 顶层返回 `lengthCheck`（unit/chars/status/label/target/deviation/suggestion/totalChars/inRangeChapters/outOfRangeChapters，多章时带 perChapter 数组）。`meta.words` 等既有字段不变。
4. **前端**（public/）：输入框实时计数器显示 `1520 字 · 偏短（目标 2000–4000）` 并按达标/不达标着色；结果区渲染「篇幅检测」卡片（判断依据 + 优化建议 + 逐章徽标）；章节行标题带单章字数状态徽标。

### 4.4 已验证

- `node --test`：73/73 全绿，零回归
- API 冒烟（`/api/analyze`）：
  - ~1730 字单章 → `short`，deviation 270，建议补冲突回合 ✓
  - ~7390 字单章 → `far-long`，deviation 3390，建议按场景拆章 ✓
  - 多章（1440 + 3790 字，chapterMode）→ 平均单章 2615 `ok`；perChapter 正确标出第一章 `short`（并触发 1 条质量扣分）、第二章 `ok` ✓

### 4.5 目标字数区间可配置（本轮新增）

硬编码 2000–4000 已升级为**前端可选三档**：1500–3000（短章）/ 2000–4000（常规）/ 3000–6000（长篇）。

- **前端**：`public/index.html` 新增「目标字数区间」选择器 `#lengthTarget`（`<select>` 三档），`public/app.js` 新增 `LENGTH_PRESETS`（三档端点）、`selectedTarget`（当前选择），change 事件实时刷新输入框计数器并按达标/不达标着色；提交时 `POST /api/analyze` 的 body 携带 `lengthTarget: selectedTarget`。
- **后端透传**：`analyzer.analyzeNovel` → `analyzeCommercialQuality` / `buildLengthReport`；`chapterAnalyzer.scanOnly` / `analyzeChapters` 的逐章 `classifyLength`；`commercialQuality.lengthUnitOf` 均透传 `input.lengthTarget`，最终决定篇幅判定、实时计数器、章节徽标与后端打分口径。
- **设计不变量**：`1000`（far-short 上界）与 `6000`（long 上界）由 `FAR_SHORT_CEILING` / `LENGTH_LONG_CEILING` 固定，前后端镜像常量一致；**仅 min/max 端点随预设切换**，避免锚定档被误改导致判定错乱。
- **测试**：主理人补 QA 用例 +6（`analyzer` / `commercialQuality` / `chapterAnalyzer` / `server` / `lengthGuard` 五个文件），覆盖透传与档位切换；`node --test` **79/79 全绿**，零回归。

## 7. 关键约定（改代码前必读）

- 零依赖、无构建；测试必须从项目根目录跑
- `src/util.js` 与 `src/platforms.js` 是叶子模块，**绝不 require 其它 src 模块**
- `chapterAnalyzer` 被 analyzer 引用，反向引用会循环依赖——analyzer 里如需章节数据，复用内部 `chaptersOf`，别 require chapterAnalyzer
- 前端无构建，不能直接复用 src 模块——`public/app.js` 里的 `LENGTH_PRESETS` / `LENGTH_FAR_SHORT_CEILING` / `LENGTH_LONG_CEILING` 等常量是 `lengthGuard.js` 的**镜像**，改档位时两边必须同步（app.js 里有注释标注对应关系）
- 评分扣分项改动要检查是否与既有检查重复惩罚（字数 900 下限就是为此设计的）
- 代码风格：具名常量（禁魔法数字）、中文 JSDoc、检查项走数据驱动表（照 QUALITY_CHECKS 组织）
